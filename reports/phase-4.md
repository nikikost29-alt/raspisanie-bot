# Фаза 4 — почему /raspisanie молчит в Actions

**1. Шаг 1, факты из API и логов.** Прогонов в репозитории на 07:54 UTC — **три, и ни одного после пуша правок** (`f14ef10`, 07:41 UTC): `33836905268` 04:27:59 UTC `Команда /raspisanie`, schedule, success, sha `7a32809`; `33820659812` 00:10:00 UTC, то же, success, sha `de380c4`; `33813207575` 22:28:26 UTC `Расписание на завтра`, **workflow_dispatch**, success. Оба воркфлоу в состоянии `state: active`. Логи (эндпоинт `/logs` требует прав админа — взял учётку из того же Git Credential Manager, которым идёт push) показывают у обоих прогонов пустой вывод шага «Разобрать команды»: старый код в не-`--dry` режиме не печатал ничего, поэтому в логе сразу за `##[group]Run python bot.py --poll` идёт следующая группа. Шаг сохранения в прогоне 00:10 отработал полностью: `[main 7a32809] state: offset команд [skip ci]` / `1 file changed, 2 insertions(+), 1 deletion(-)` / `de380c4..7a32809  main -> main`. В прогоне 04:28: `state.json не менялся, коммит не нужен` — то есть `getUpdates` вернул ноль апдейтов, очередь была пуста, команды пришли позже.

**2. Шаг 2, какое подозрение подтвердилось.** Ни (а), ни (в). **(а) опровергнуто:** прогон 04:28 шёл на `7a32809` — это и был HEAD на тот момент, а `state.json` на origin содержит `"offset": 866805460`, ровно то, что записал прогон 00:10; ни устаревшего кода, ни отката состояния нет. **(в) опровергнуто:** коммит и push из воркфлоу прошли успешно, строки push в логе выше, прав `contents: write` хватило. **(б) подтверждается частично и задним числом:** мой локальный `--poll` в 07:41 UTC действительно забрал апдейты `866805460..465` и ответил на 4 команды, после чего я подтвердил очередь — но к тому моменту команды уже висели неотвеченными около трёх часов, так что локальный запуск не причина молчания, а причина того, что ответы вообще появились. **Настоящая причина, доказанная числами: прогонов по расписанию просто нет.** При кроне `*/5` за девять часов жизни репозитория `command.yml` запускался дважды, а с 04:28 до 07:54 UTC — ни разу; `daily.yml` по расписанию не запускался **ни разу**, единственный его прогон был ручным. Отсюда же поправка к твоей вводной: вечерняя рассылка «в 10:40 в группу» — это не Actions, а те самые 4 ответа моего локального `--poll` в 10:41 по Москве, они выглядят как расписание, потому что это и есть расписание на сегодня.

**3. Шаг 3, что изменил** (коммит `c857ea9`). `bot.py`: offset пишется на диск сразу после каждого удачно отправленного ответа, а не одним махом в конце; id отвеченных команд копятся в `state["answered"]` (хвост 200 штук), и если тот же апдейт достанется второму читателю очереди, он его пропустит, а не ответит повторно; в лог добавлены id всех пришедших апдейтов, пометка каждого распознанного как команда, чат и `message_id` отправленного ответа, записанный offset и состояние privacy mode. Новый `merge_state.py` сливает два состояния: offset берётся больший, `answered` объединяются, в `sent` при совпадении даты выигрывает более свежий `ts`. Шаг «Сохранить state.json» в обоих воркфлоу переписан: до пяти попыток `push`, при отклонении — `fetch` + `reset --hard origin/main` + слияние через `merge_state.py` + повтор, а после пяти неудач шаг падает с ненулевым кодом, а не молчит.

**4. Что проверено фактически.** YAML обоих воркфлоу разбирается (`yaml ok`, код 0). Синтетика с подменёнными `get_updates`/`send`, настоящий Telegram не трогался: три команды подряд, сбой на третьей → в state остался `offset 102`, то есть ровно на сбойной команде, `answered = [100, 101]`, исключение проброшено; повторная выдача тех же трёх апдейтов дала **одну** отправку вместо трёх — первые две отсеялись по `answered`. `merge_state.py` на паре состояний (наше `offset 105`, чужое `offset 130`) вернул `offset=130`, `answered=[100,101,128]`, текст за 05.09 взял из более свежего по `ts`.

**5. Что осталось недоказанным.** Шаг 4 не закрыт: прогона по расписанию на новом коде **ещё не было**, доказать работу команды в Actions пока нечем — ждёт фоновое наблюдение за API, которое поймает первый же schedule-прогон `command.yml` и вытащит его лог. Само расписание починить кодом нельзя: `*/5` GitHub соблюдать не обязан и по факту не соблюдает, так что даже с исправленным ботом ответ на `/raspisanie` будет приходить с задержкой в часы. Реальные варианты — вебхук (ты его запретил), внешний пингер, дёргающий `workflow_dispatch`, либо цикл опроса внутри одного прогона, чтобы он покрывал минут пять вместо мгновения. Локальный `--poll` я больше не запускаю.
